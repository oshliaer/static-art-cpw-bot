# Static Art CPW Bot

> **Проект останавливается 7 сентября 2026 года.** В этот день Yandex AI Studio отключает модель и API, на которых он построен. Код заморожен в рабочем состоянии и больше не развивается, причина описана ниже -- она внешняя и неустранимая в рамках этой архитектуры. Репозиторий опубликован как история: работающий пример связки Apps Script + Yandex ART + Telegram, который прожил свой срок. За время работы, с 17 апреля 2025 года, сделано 509 запусков, 506 из них дошли до публикации в канале. Данные приведены на 4 сентября 2026 года, бот ещё работает.

Ежедневный генератор изображений в двуцветной графике. Google Apps Script раз в сутки отправлял в Yandex ART один и тот же короткий запрос с новым зерном генерации, дожидался готовности картинки и публиковал её в Telegram-канал [@static_art_cpw](https://t.me/static_art_cpw). Вся история генераций велась в Google Таблице.

## Про портреты никто не просил

Самое интересное в проекте не в коде. Запрос к модели был предельно коротким: несколько слов про технику рисования, три цвета в hex и пара слов о теме. Ни слова "портрет", ни слова "лицо", ни слова "человек" в нём нет. Единственное, что менялось от запуска к запуску, -- зерно генерации.

Портреты, фасы, профили, пейзажи -- всё это модель выбрала сама. Из скупого описания палитры и техники рисования она раз за разом доставала женские лица общего типажа или киберпанковской тематики. Проект в итоге оказался не столько генератором картинок, сколько длинным наблюдением за тем, что модель считает уместным нарисовать, когда ей почти ничего не сказали.

Сам текст запроса не публикуется и хранится в Script Properties проекта Apps Script.

## Что делало приложение

Точка входа одна, её вешали на ежедневный триггер:

```js
function loop() {
  new App().generateDailyART();
}
```

Каждый запуск выполнял один из двух шагов, в зависимости от состояния строки за сегодняшний день на листе `Daily ART`. Такая двухфазная схема нужна была потому, что старый Yandex ART работал асинхронно: запрос возвращал не картинку, а операцию, готовность которой надо было опрашивать отдельно.

### Чтение таблицы

Оговорка сразу: читать лист целиком -- решение стартового проектирования, а не образец. Там, где записей ожидается много, так делать не стоит. Но сервис не рассчитывал и на сто тысяч генераций за всю жизнь, поэтому подход выбран самый простой.

Лист читается целиком и превращается в коллекцию объектов с ключами из заголовка. Заголовки приводятся к нижнему регистру, поэтому порядок колонок в коде не зашит, а каждая ячейка помнит свои координаты:

```js
const headers = data[0].map((header, index) => {
  if (typeof header !== 'string' || header.trim() === '') {
    return `__col_${index}`;
  }
  return header.toLowerCase();
});

headers.forEach((header, __colIndex) => {
  obj[header] = { __value: row[__colIndex], __colIndex, __rowIndex };
});
```

Дальше среди строк ищется сегодняшняя, по совпадению отформатированных дат в часовом поясе таблицы.

### Фаза первая: заказ картинки

Если строки за сегодня нет, подбирается свободное зерно:

```js
const taken = this.seedsSheet
  .getRange('A:A')
  .getValues()
  .map((row) => Number(row[0]))
  .filter((value) => Number.isFinite(value) && value > 0);

let seed;
do {
  seed = Math.floor(Math.random() * Number.MAX_SAFE_INTEGER) + 1;
} while (taken.includes(seed));
```

С этим зерном уходит запрос в Yandex ART. Ответ содержит не картинку, а идентификатор операции:

```js
imageGenerationAsync(seed) {
  const httpRequest = UrlFetchApp.fetch(
    'https://llm.api.cloud.yandex.net:443/foundationModels/v1/imageGenerationAsync',
    {
      method: 'POST',
      headers: { Authorization: `Bearer ${this._token}` },
      contentType: 'application/json',
      payload: JSON.stringify({
        model_uri: this._model,
        messages: [{ text: this._message, weight: 1 }],
        generation_options: { mime_type: 'image/jpeg', seed },
      }),
    },
  );
  const response = JSON.parse(httpRequest.getContentText());
  if (response.error) {
    throw new Error(`Yandex ART API error: ${response.error.message}`);
  }
  return response;
}
```

Строка дописывается в таблицу, и сразу за этим зерно перезаписывается текстом, иначе шестнадцатая цифра потеряется:

```js
const row = headers.map((h) => item[h]?.__value ?? '');
this.dailyArtSheet.appendRow(row);
this.writeSeed(this.dailyArtSheet.getLastRow(), headers, nextSeed);
```

```js
writeSeed(rowIndex, headers, seed) {
  const colIndex = headers.indexOf('зерно');
  if (colIndex === -1) {
    return;
  }
  this.dailyArtSheet
    .getRange(rowIndex, colIndex + 1)
    .setNumberFormat('@')
    .setValue(`'${seed}`);
}
```

На этом запуск заканчивается. Картинки ещё нет.

### Фаза вторая: получение и публикация

Следующий запуск находит строку за сегодня, видит записанный id операции и пустой отчёт, и опрашивает операцию. Как только приходит изображение в base64, оно превращается в blob и уходит в канал:

```js
const request = this.ya.operations(id);
if (request.response?.image) {
  const image = request.response.image;
  const blob = Utilities.newBlob(Utilities.base64Decode(image), 'image/jpeg', 'image.jpg');
  const tgResp = this.telegram.sendPhoto(blob);
  if (tgResp.ok === true) {
    item['результат отправки картинки'].__value =
      `https://t.me/static_art_cpw/${tgResp.result.message_id}`;
  }
  item['отчет'].__value = 'Готово';
}
```

Отправка в Telegram -- обычный `sendPhoto`, blob уходит как поле `photo` в теле запроса:

```js
sendPhoto(photo, extra = {}) {
  const url = `https://api.telegram.org/bot${this._token}/sendPhoto`;
  const payload = Object.assign({ chat_id: this._chatId, photo }, extra);
  const httpResponse = UrlFetchApp.fetch(url, {
    method: 'post',
    muteHttpExceptions: true,
    payload: payload,
  });
  if (httpResponse.getResponseCode() !== 200) {
    throw new Error(`Error sending message: ${httpResponse.getContentText()}`);
  }
  return JSON.parse(httpResponse.getContentText());
}
```

Строка перезаписывается целиком, поэтому текстовое зерно после этого восстанавливается:

```js
this.dailyArtSheet
  .getRange(item.дата.__rowIndex + 1, 1, 1, headers.length)
  .setValues([headers.map((h) => item[h]?.__value ?? '')]);
this.writeSeed(item.дата.__rowIndex + 1, headers, item.зерно?.__value ?? '');
```

## Почему проект остановлен

Идея проекта держалась на параметре `seed`. При неизменном тексте запроса одно и то же число всегда давало одно и то же изображение, значит по своему числу человек мог получить свою персональную картинку, а поле возможных работ упиралось в `Number.MAX_SAFE_INTEGER`.

7 сентября 2026 года Yandex AI Studio отключила модель `art://<folder_id>/yandex-art-2.0` и вместе с ней старый асинхронный API генерации изображений. Замена -- модель `aliceai-image-art-3.0`, доступная только через новый Images API, совместимый с OpenAI. У этого API другой контракт: он синхронный, отдаёт картинку сразу, и **параметра `seed` в нём нет**. Обращение в поддержку 26 августа 2026 года подтвердило: задать зерно в Images API нельзя, способа воспроизвести ранее сгенерированное изображение не существует.

Это не задача на переписывание клиента. Без `seed` пропадает воспроизводимость, а вместе с ней -- сама идея "изображение по вашему номеру". Поэтому вместо миграции проект остановлен.

## Схема таблицы

Три листа. Данные пишет только `Daily ART`, остальные два -- представления на формулах.

**`Daily ART`**, по строке на день. Заголовки читаются из первой строки и приводятся к нижнему регистру, поэтому порядок колонок в коде не зашит:

| Колонка | Что в ней |
|---|---|
| `Дата` | Дата запуска |
| `Зерно` | Использованное зерно генерации |
| `Запрос картинки` | id операции Yandex ART либо текст ошибки |
| `Результат запроса картинки` | `Получено`, когда картинка забрана из операции |
| `Результат отправки картинки` | Ссылка на пост в канале либо текст ошибки |
| `Отчет` | `Готово` после успешной публикации |

**`Seeds`** -- отсортированный список занятых зёрен, одна формула в `A1`:

```
={'Daily ART'!B1;SORT('Daily ART'!B2:B)}
```

Именно этот лист читает геттер `nextSeed`, когда подбирает свободное число.

**`Dice`** -- зеркало колонки со ссылками на посты, одна формула в `A1`:

```
={'Daily ART'!E:E}
```

Кодом не используется.

## Известные дефекты

Найдены при разборе таблицы перед публикацией.

**Записанное зерно не всегда равнялось отправленному. Исправлено 2 сентября 2026 года.** Зерно клалось в ячейку строкой с ведущим апострофом, `` `'${nextSeed}` ``, в расчёте на то, что Таблицы сохранят его текстом. Расчёт не оправдался: у колонки `Зерно` был задан числовой формат `NUMBER` с шаблоном `0`, а заданный формат сильнее ведущего апострофа. Число же в Google Таблицах хранится с точностью до 15 значащих цифр, тогда как зерно занимает до 16.

Результат виден на данных. Из 506 строк, записанных до починки, 321 хранит зерно числом и 185 текстом. Все 262 шестнадцатизначных зерна, попавшие в ячейку числом, оканчиваются на ноль -- последняя цифра потеряна. Среди 185 шестнадцатизначных, сохранённых текстом, на ноль оканчивается ровно одно, как и ожидается от случайных чисел.

Практический смысл: больше чем для половины архива записанное в таблице зерно отличается от того, что реально ушло в Yandex ART. Воспроизвести по нему картинку было нельзя ещё до того, как Yandex убрал `seed` из API. Проект потерял воспроизводимость дважды: сначала тихо, на границе типов Google Таблиц, потом окончательно, вместе с отключением API.

Правильная работа с таким значением состоит из двух половин, и нужны обе.

**На запись** зерно уходит в ячейку с ведущим апострофом, `` `'${seed}` ``. Апостроф говорит Таблицам, что значение текстовое, и в сохранённое значение не попадает. Метод `writeSeed` дополнительно ставит ячейке формат `@`, чтобы числовой формат колонки не перебил апостроф.

**На чтение** значение приходит строкой, поэтому его нужно привести к числу. Геттер `nextSeed` больше не сравнивает напрямую: `Number(row[0])` с отсевом `NaN`, и только потом `taken.includes(seed)`. Без этого шага строгое равенство не совпало бы никогда, и проверка уникальности перестала бы работать вовсе.

Приведение к числу здесь не косметика. Зёрна попадают в таблицу двумя путями: генератор пишет их текстом, а оператор вносит вручную числа, которые называют люди, когда просят картинку по своему номеру. В ячейке эти два вида лежат по-разному, и сравнивать их можно только после приведения к общему типу.

Так же исправлена вторая фаза: `setValues` переписывает строку целиком, включая зерно, поэтому после неё текстовая запись зерна восстанавливается.

Проверено на запусках 3 и 4 сентября: зёрна записаны текстом, все 16 цифр на месте.

**Проверка уникальности нужна по-настоящему.** Легко посчитать, что при диапазоне до 9007199254740991 вероятность коллизии пренебрежимо мала, и решить, что проверка лишняя. Это верно только для равномерно случайных зёрен. Числа, которые называет человек, равномерными не бывают: даты, круглые, короткие. Два человека вполне могут попросить одно и то же число, и именно от этого проверка и защищает. Считается занятым то зерно, что попало на лист `Daily ART` в колонку `Зерно`: лист `Seeds` -- зеркало этой колонки, и читает `nextSeed` именно его.

**Три запуска из 509 не дошли до публикации.** У строк за 9 апреля 2026, 13 августа 2026 и 3 сентября 2026 есть id операции, но нет ни картинки, ни отчёта. Последняя из них -- вторая строка за тот же день, рядом с успешной. Похоже на два пересекающихся запуска триггера, но это только предположение.

## Сборка

Сборка устроена на gulp и clasp: файлы из `src/` копируются в `build/`, туда же кладётся `.clasp.json` из выбранного окружения, после чего запускается `clasp push`.

```sh
npm install
npm run dev    # push в dev-проект, режим наблюдения
npm run prod   # push в prod-проект
```

Для работы нужен установленный и авторизованный [clasp](https://github.com/google/clasp). В `settings/prod/.clasp.json` идентификатор проекта пустой -- боевой проект в репозитории не зафиксирован.

В репозитории два конфига ESLint, и это намеренно: корневой `.eslintrc` описывает окружение Node для тулинга репозитория, `src/.eslintrc` -- окружение Apps Script для кода приложения. Это разные машины исполнения. Скрипт `npm run lnsett` подкладывает второй конфиг ещё и в `settings/`.
